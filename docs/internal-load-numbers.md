# Internal load numbers

Applied to the connected Supabase project on 2026-10-31. Migration history and the checked-in migration both use `20261031173226_unique_internal_load_numbers.sql`.

- `loads.id` remains the UUID relational identity. No document, assignment, accounting or historical settlement relationship was changed.
- `loads.internal_number` is a global bigint `GENERATED ALWAYS AS IDENTITY`, starting at 100, with a unique constraint, minimum 100 and a non-cycling sequence. A trigger also rejects resetting a row to a new DEFAULT number. Clients never choose the next number.
- Deleted or rolled-back allocations are not reused. Gaps are allowed; numbers continue beyond 999.
- Existing rows were backfilled as 100, 101 and 102 without firing UPDATE triggers. Their UUIDs, broker references, versions and updated timestamps remained unchanged. The next successful creation starts at 103, unless another creation/rollback has consumed it.
- `loads.load_number` remains the original broker reference. It can repeat and retains a company/reference search index. The previous company/reference unique constraint and frontend reference-only duplicate block were removed.
- Exact-file import retries still use the existing checksum/import UUID binding. A repeated broker reference does not mean two separate documents are the same shipment.
- Web list models expose `internalNumber`, `brokerLoadNumber`, and a primary display `loadNumber` such as `#100`. The broker reference is shown separately on load cards, the driver roster, map selection, document registry and broker details. Both references remain searchable.
- Finance RPC rows include `internal_number`, and analytics use it as the primary reference. Previously confirmed settlement snapshots/PDFs remain unchanged.
- Manual creation accepts an optional broker reference. The internal number is generated by Postgres at actual creation, not during PDF preview or by browser state.

Verification: 970 Node tests, lint, i18n parity and build passed. An isolated Postgres test verifies backfill/history preservation, repeated broker references, explicit/reset-number rejection, deletion/rollback non-reuse, 16 concurrent inserts, and tenant/anonymous isolation. The 204-row financial snapshot/role-isolation test also passes after the migration. Production read-back confirms three unique numbers, ALWAYS identity, no cycle, unchanged versions/timestamps and the security-invoker view. Security/performance advisory categories are unchanged.

The PDF extraction Edge Function was not deployed or changed by this release. Existing mobile clients can keep using broker references while retaining UUID-based relationships; displaying the new internal number in a separate mobile application requires that client to consume the new field.
